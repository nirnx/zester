# APT repository (`zester.cc/repo`)

Zester publishes a signed APT repository to GitHub Pages at
`https://zester.cc/repo`, alongside the docs site. Debian/Ubuntu users install
and upgrade with the normal `apt` flow — see
`website/content/docs/getting-started/installation.mdx` for the consumer steps.

## How it works

GitHub Pages serves **one artifact** for the whole `zester.cc` domain, and it is
built by the Pages workflow (`.github/workflows/docs.yml`) from `website/out`.
So the repo cannot be its own deployment — it rides inside the same artifact.

- **`apt-repo` branch** — the durable pool-of-record. Holds `pool/` (every
  published `.deb`), the regenerated `dists/` metadata, and the exported public
  keys (`zester.gpg`, `zester.asc`). Keeps binaries out of `main`'s history.
- **`release.yml`** (on tag `v*`) — after `make deb-all`, imports the signing
  key, runs [`publish-repo.sh`](./publish-repo.sh) against a checkout of the
  `apt-repo` branch (stages the new `.deb`s into the pool, regenerates + signs
  `dists/`), commits, and pushes `apt-repo`. It then calls the Pages workflow so
  the new version is live immediately.
- **`docs.yml`** (on push to `main`, or called by `release.yml`) — builds the
  docs, overlays the `apt-repo` branch into `website/out/repo/`, and deploys.
  The signing key is **never** needed here — docs pushes only copy the branch.

`publish-repo.sh` is deterministic: `dists/` is regenerated from the pool on
every run, so re-running a release is safe. The pool (the `.deb` files) is the
only state.

## One-time setup: signing key + secrets

The repo's `Release` file is GPG-signed so `apt` can verify authenticity over
HTTP. Generate a signing key once and add it to the repo's Actions secrets.

```bash
# 1. Generate a signing key (RSA 4096, no expiry). Use a dedicated identity.
gpg --batch --gen-key <<'EOF'
Key-Type: RSA
Key-Length: 4096
Name-Real: Zester Repository Signing Key
Name-Email: security@zester.cc
Expire-Date: 0
%no-protection
EOF
#   Drop `%no-protection` and add `Passphrase: <pass>` if you want a passphrase
#   (then also set the GPG_PASSPHRASE secret below). A passphrase stored as an
#   adjacent Actions secret adds little over the key secret itself, so
#   passphraseless is a common, reasonable choice for automated repo signing.

# 2. Find the key id / fingerprint.
gpg --list-secret-keys --keyid-format=long security@zester.cc

# 3. Export the private key (this is the GPG_PRIVATE_KEY secret value).
gpg --armor --export-secret-keys security@zester.cc | pbcopy   # macOS
# gpg --armor --export-secret-keys security@zester.cc | xclip   # Linux
```

Add to **Settings → Secrets and variables → Actions**:

| Secret | Value | Required |
|--------|-------|----------|
| `GPG_PRIVATE_KEY` | armored private key from step 3 | yes |
| `GPG_PASSPHRASE`  | passphrase, if the key has one | only if passphrase-protected |

Back up the private key somewhere safe (e.g. a password manager). If it is ever
lost or rotated, every consumer must re-import the new public key — plan
rotation deliberately.

## Repository parameters

Defaults live in `publish-repo.sh` / `release.yml`: suite `stable`, component
`main`, architecture `amd64`, origin/label `Zester`. Change them by overriding
the `APT_*` env vars in `release.yml`.

### Adding arm64 (future)

`release.yml` currently builds `amd64` only (`make deb-all GOARCH=amd64`). The
`Packages` index is generated by scanning the whole pool per architecture, which
is correct only while the pool is single-arch. To add `arm64`:

1. Build both arches in `release.yml` (`make deb-all-arch` produces amd64 +
   arm64 `.deb`s).
2. Either switch `publish-repo.sh` to **reprepro** (which filters by
   architecture natively and dedups the pool) or split the pool into
   arch-specific subdirectories and scan each separately. A flat pool scanned
   per-arch would wrongly list every arch's packages in each `binary-<arch>`
   index.
3. Set `APT_ARCHS="amd64 arm64"`.

## Local dry run

`apt-ftparchive` ships in `apt-utils` (Debian/Ubuntu; not macOS). On a Linux box:

```bash
mkdir -p /tmp/zrepo
GPG_KEY_ID=<your-key-id> ./publish-repo.sh /tmp/zrepo /path/to/dir/of/debs
find /tmp/zrepo -maxdepth 4 -type f
```

## Troubleshooting

- **Pages deploy from the release run is rejected** — the `github-pages`
  environment may restrict deployments to specific branches. In **Settings →
  Environments → github-pages**, set deployment branches/tags to allow tags
  (e.g. `v*`) or "No restriction". (Most setups allow all by default.)
- **`apt update` reports NO_PUBKEY** — the consumer hasn't imported
  `zester.gpg`, or the key was rotated. Re-run the install step 1.
- **`apt update` reports the repo is not signed / GPG error** — `InRelease`
  failed to generate. Check the `GPG_PRIVATE_KEY` secret and (if set)
  `GPG_PASSPHRASE` in the release run logs.
