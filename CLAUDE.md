# Zester

Go-based infrastructure automation system (SaltStack alternative). Module path: `github.com/nirnx/zester`.

> ## ⚠️ SUPER IMPORTANT — Model policy (read first)
>
> This project runs on **Claude Fable 5**. Every subagent, Workflow `agent()` call,
> and Agent-tool spawn **MUST be pinned to Fable** (`model: 'fable'`). Do **not**
> rely on model inheritance — in this environment unpinned subagents fall back to
> the harness default (**Opus**), which the maintainer does not want.
>
> **If anything triggers a switch from Fable to Opus** (an unpinned agent, a
> Workflow run started before the pin was added, a harness fallback, or a session
> default reset — anything you observe running on Opus):
> 1. **STOP** the offending run immediately (`TaskStop`) rather than letting it finish.
> 2. **FLAG** it to the maintainer: say what switched, the root cause, and which
>    run/agent was affected.
> 3. **SUGGEST the operating pattern** that prevents a recurrence (e.g. "pin
>    `model: 'fable'` on all N `agent()` call sites in the script") and apply it to
>    the script/config.
> 4. **NOTIFY and hand back** — do NOT silently relaunch. Let the maintainer
>    restart the run with that rule in place.
>
> Belt-and-suspenders: `teammateDefaultModel` should be `claude-fable-5` (set via
> `/config`) so subagents default to Fable even if a pin is missed — but the
> explicit per-call pin remains mandatory, not optional.

## Architecture

Five binaries in `cmd/`. Daemon `main.go`s own ONLY flag parsing, config loading, logging setup, and signal handling (~90 lines each); runtimes live in `internal/masterd` (`Daemon`) and `internal/peeld` (`Agent`), each `New(cfg *config.MasterDaemonConfig, logger)` + `Run(ctx)`.

- **zester-master** — Dispatches jobs, compiles settings, watches facts; runs heartbeat, orphan scanner, `schedule-results` consumer, target-resolution service, enrollment admin service, rollout resume loop, and the reactor (see Reactor & Events; config section `reactor.*`, enabled by default, `--reactor`, `--reactor-dir`, …). Sched-consumer and reactor boot failures spawn 60s retry loops that flip their readiness checks to OK on success. Emits `zester.event._master.enroll.pending.<id>` on new enrollment records (`enroll.HandlerConfig.OnPending` hook, best-effort, emitted regardless of `reactor.enabled`). Two advisory `bus.LeaderLease`s (see Multi-Master Coordination): `"publisher"` gates settings-files/state-files/reactor-files publish + GitFS sync; `"facts-secrets"` gates secrets re-encryption. `--config` (default `/etc/zester/master.yaml`). Serves `/healthz` (liveness), `/readyz` (checks: `nats`, `enroll-server`, `sched-consumer`, `target-service`, `gitfs` when enabled, `reactor` when enabled), `/metrics` (Prometheus) on `--health-addr` / `health_addr` YAML (default `127.0.0.1:9091`). `--log-level` / `--log-format` (JSON default) via `internal/logging`. Config structs in `internal/config/master_daemon.go`; **flags are generated from `flag:"..." usage:"..."` struct tags via `config.BindFlags`, user-set flags re-applied after YAML load via `config.ApplyVisited` (`internal/config/bind.go`) — a new knob is ONE tagged struct field; precedence: flag > YAML > struct default.**
- **zester-peel** — Agent on managed nodes; runtime in `internal/peeld`. **Offline-first startup**: `Agent.Run` splits into a LOCAL phase (health server, enrollment, NATS client with `RetryConnect`, local fact collection via `facts.Manager.Collect`, provider detection, `ModuleContext`, states engine, settings warm-start from snapshot `/data/settings-snapshot.msgpack`, scheduler, exec+cancel core-NATS subscriptions) and a CONNECTED-phase goroutine (facts publishing, master curve pub, initial settings resolve, basket publisher, settings watchers, statefiles sync/watch, peel heartbeat, beacon manager — v1: the `service` beacon from the `beacons:` settings key, hot-reloaded) that starts once NATS is healthy — a peel booted during a NATS outage enforces from local state and self-heals (the bus `nats.ConnectHandler` flips `IsHealthy` on a deferred initial connect). Only genuinely local errors (bad config, missing creds + no master URL, bad TLS) are fatal. **Execution model**: mutating executions go through a bounded 64-slot queue consumed by one worker holding `execMu` (queue-full replies immediately `"peel busy: execution queue full"`; queued jobs cancelable); the read-only set — `facts.*` EXCEPT `facts.set`, `settings.*`/`pillar.*`, `test.ping`, `grains.*`, `sys.list_functions` — runs concurrently OUTSIDE `execMu` on immutable contexts from `mctxTemplate.WithFactsSettings(...)`, so `test.ping`/fact queries answer during long highstates. Dispatches are **acked on accept** (`job.Ack` on `bus.JobAckSubject`, after fencing/dedup, before execution) and **deduped** via persisted jid→epoch state (`/data/peel-dedup.msgpack`, 0600, 4096-entry cap; `ObserveDurable` flushes synchronously before an accepted job executes; epoch ≤ stored rejected — `pkg/job` CAS-bumps `Epoch` on every legitimate redispatch, so failover is unaffected). **Exec dispatch order** (`execModule` in `internal/peeld/exec.go`): nil-`Args` guard → `state.apply`/`state.highstate` → `facts.*` → `settings.*` (+ `pillar.*` alias) → `event.send` (special-cased — needs the bus; mutating serialized path; bare positional = tag, slash or dotted; remaining args → `Event.Data`; depth stamped from `ExecRequest.ReactorDepth`; errors when NATS is down) → `pkg/execmod` function (only when the name is NOT a registered state module — checked live via `registry.Has`) → state-module build via the Registry with the request's state ID as primary-param default; ad-hoc runs wrapped with `state.WrapAttributes(state.ParseStateAttributes(args), guardRunner)`. **Startup states** (`startup_states: highstate|sls` + `startup_sls_list`, Salt parity; `internal/peeld/startup.go`): one-shot boot-time apply on the serialized exec path, retrying with capped backoff while the peel is coming up (statesEngineUnavailable / settings-never-resolved are the ONLY retried responses) — a freshly enrolled peel converges autonomously; invalid config is boot-fatal; recurring enforcement stays with the scheduler. Publishes facts `zester_version` and `protocol_version`. `--config` (default `/etc/zester/peel.yaml`). Serves `/healthz`, `/readyz` (checks: `nats`, `kv`), `/metrics` on `health_addr` (default `127.0.0.1:9090`; distinct from master's `:9091` so both can colocate). `--master-urls` / `master_urls` YAML: ordered enrollment-URL failover list, precedence over single-URL `master_url` when non-empty (`--master-urls ""` clears a YAML list). Config structs in `internal/config/peel.go`; same binder convention.
- **zester** — Operator CLI. Salt-style execution `zester '<target>' <module.function> [args...]` with `--format text|json|yaml`, `--no-color`, `--test` (sets `test=True` in module args; a literal `test=True` arg works too — peel runs `ModeTest`), `--direct` (bypass master, NATS request/reply straight to peels). Job mode resolves targets via the master resolve service (`target.NewServiceLister` over `zester.target.resolve`, automatic facts-KV-scan fallback with stderr Warn) and stamps `Job.TargetExpr` (audit); `--direct` keeps the pure KV lister. `zester job list` skips `active.<jid>` index keys; `job active` enumerates the active-jobs index (no full-bucket scan); `job show` reads per-peel return keys. `zester peel list` shows `PEEL ID / OS / ARCH / ONLINE / LAST-SEEN` from the `peel-heartbeat` bucket (absent key = offline; missing bucket = `-`; 60s freshness backstop). `zester update status` has trailing DEGRADED and PROTO columns (`-` = protocol 0 = never reported). `zester enroll approve|reject|revoke` go over NATS request/reply; `--direct-kv` is the break-glass direct-KV path; `enroll approve --force` overrides a trust-mismatch refusal; `enroll approve` targets by enrollment ID, `--peel <id>` (resolves the current record via the KV index — no KSUID copying), or `--all-pending` (exactly one selector); `enroll list` gains a TRUST column (`ok`/`unverified`/`MISMATCH!`/`-`). `zester ca init|fingerprint|print|issue` is the **offline** embedded-CA command group (no NATS; `--dir` default `/var/lib/zester/auth/ca`): `init` generates the root+intermediate hierarchy and prints the SPKI pin, `issue nats-server|enroll` mints server certs (`issue nats-server` also drops the CA root as `nats-ca.crt` next to the cert — the peel trust anchor). `zester nats-auth init` (renamed from `zester auth init` in 0.3.5) is the **offline** NATS-auth bootstrap (`cmd/zester/cmd/auth.go`): generates the operator/account/system JWTs + `account.seed` + `master.creds`/`admin.creds` + a `nats-server.conf` (operator mode, MEMORY resolver, JetStream, **`max_control_line: 16384`** — a peel JWT exceeds NATS's 4096 default and is rejected PRE-auth with "maximum control line exceeded" otherwise; ANY externally-run nats-server MUST set this) — the trust plane paired with `zester ca`'s TLS plane; NATS itself stays external (no server binary shipped). `zester nats-auth lint <creds-file>...` (offline) decodes a `.creds` JWT and flags JetStream grant gaps (missing `$JS.FC.<stream>.>` flow-control pub, missing `_INBOX` sub) **and oversized JWTs (CONNECT line > 4096, `LintJWTSize`)** — the class that silently denies one op / bricks a connect. `zester update fetch` downloads a published binary from the update-binaries object store (`--component/--version` via the manifest, or `--object-key <k> --sha256 <h>` direct — the watchdog's own path; `--out` writes it); `--creds <peel.creds>` verifies peel creds can complete the flow-controlled download. The CLI resolves NATS CA/creds from `--nats-ca`/`NATS_CA_FILE`/`--creds` (or `--master`/`NATS_URL`) with NO config file — a peel-only box needs no `~/.zester/config.yaml`. `zester event send <tag> [k=v...]` publishes as the `_admin` origin (slash or dotted tag; flush-before-exit); `zester event watch [match-glob]` subscribes `zester.event.>` with client-side match-key filtering; `zester reactor test <match-key> [--data k=v] [--event-json ...]` dry-runs the live rule set over `zester.reactor.test` (a no-responders error hints no reactor-enabled master is running).
- **zester-watchdog** — Process supervisor for self-updates; wraps zester-peel or zester-master. Uses `flag` package (not Cobra). Details (slots, supervisor, soak/readiness, flags, enrollment-aware behavior) under Self-Update System.
- **zester-migrate** — Salt→Zester migration: `zester-migrate [--write] [--rename-vars] <path>` converts `.sls` to `.zy` via `pkg/migrate`, prints a change/warning report, exits 1 when warnings need manual review. Uses `flag` package (not Cobra).

Dev CLI in `playground/`: **zester-cli** (`zester-cli <target> <module> [args...]`) for direct peel access; prefer `zester --direct`.

### Package Layout

| Package | Purpose |

| `pkg/beacon` | Peel-side beacon engine. v1 ships ONE beacon — `service` — polling `exec.ServiceExec` running state and emitting transition events on `bus.BeaconSubject(peelID, "service")` (tag `beacon/<peelID>/service`, data `{service, running, previous}`). Full beacon set (disk/mem/load/filewatch) is Phase 2. |
| `pkg/update` | Self-update system: `SlotManager`, `Supervisor`, `Handler`, `Manifest`/`BinaryStore`, `Reporter`, `RolloutController`. Details under Self-Update System. |
| `pkg/auth` | NKey/Curve25519 key management, encryption, JWT grants. Peel JWTs are least-privilege (`PeelUserJWTOptions`): job ack/return/schedule publish, own facts/basket/heartbeat writes, own-event publish (`zester.event.<peelID>.>` — feeds the reactor; NO `zester.event.>` subscribe, no reactor/admin grants), settings/secrets/state-files reads, publish on `zester.target.resolve`, plus the update-plane grants for the colocated watchdog (update-status put, update-binaries object-store read). **JetStream ordered/push consumers (object-store download, KV watches) also require FC-publish grants `$JS.FC.<stream>.>` — the client library mints those subjects at runtime, so they're invisible to static scans; a missing one silently stalls the op with a `permissions violation` (bit us twice: the update-status key, then `$JS.FC.OBJ_update-binaries.>`). `lint.go` (`zester nats-auth lint <creds>`) decodes a creds JWT and flags these gaps offline (consumer-create on a stream ⇒ needs `$JS.FC.<stream>.>` pub + an `_INBOX` sub; OBJ_ gap = error, KV_ gap = warn). Backed at runtime by an integration permissions-sentinel + a real watchdog-download test.** Admin JWTs (`AdminUserJWTOptions`): `zester.admin.>`, `zester.target.resolve`, pub `zester.event._admin.>` (`zester event send`) + `zester.reactor.>` (`zester reactor test`), sub `zester.event.>` (`zester event watch`) — pre-reactor admin creds work degraded (no event/reactor CLI) until re-issued. A peel whose creds lack the heartbeat/resolve grants looks offline in presence views (heartbeat puts fail at Debug, retried every tick) and falls back to facts-KV scans for basket resolution (degraded, not broken). |
| `pkg/template` | Jinja2-style `.zy` template engine. Salt-compat `salt['mod.func'](...)` accessor (`module_accessor.go`) dispatches execution-module calls during rendering via `EngineConfig.ModuleFn`. Source-scan based: a regex pre-scans for **literal** `salt[...]` subscripts (gonja has no dynamic-subscript hook), so dynamic names (`salt[var]`) and `salt[...]` inside `{% include %}`d files need the `salt_call('mod.func', args..., kw=...)` fallback. The peel wires `ModuleFn` to `moduleDispatch` (`internal/peeld/dispatch.go`): `grains.get/item/items` → local facts, `pillar.*`/`settings.*` → cached settings, everything else → `pkg/execmod` (positional `arg[0]` best-effort mapped to `name`), bounded by the 60s `moduleDispatchTimeout`. |
| `pkg/proto` | Shared message types (ExecRequest/ExecResponse, StateResult) + wire versioning (`version.go`); `ExecRequest.ReactorDepth` (msgpack `rdepth,omitempty`, additive) threads reaction chain depth into peel-side `event.send`. Additive-only policy normative in `doc.go`; key-set conformance tests pin the exact encoded keys. Details under Codec & Protocol Versioning. |
| `pkg/target` | Target matching (glob, pcre, fact, settings, compound, list) + master-side resolution service (`service.go`); `ParseType`. Details under Target Resolution Service. |
| `pkg/enroll` | Peel enrollment: state machine (`Record`, `State`), KV store (`Store`), challenge nonces (`ChallengeStore`), credential issuance (`CredentialIssuer`), HTTP `Handler`/TLS `Server`, peel `Client`, admin wire types `AdminRequest{id, operator, reason, force}`/`AdminResponse{record, err}` (`admin.go`, msgpack), file persistence helpers. `ValidatePeelID` (`verify.go`): `^[a-zA-Z0-9][a-zA-Z0-9_-]*$`, max 128 chars — no dots, no leading `_` (reserved for `_master`/`_admin` event origins), no NATS wildcards. `SanitizePeelID(raw)` (`verify.go`) maps an arbitrary string (hostname/FQDN) into a valid id — byte-wise, `.` → `_` (`peelIDDotSub`, collision-free: valid hostnames use `-`/`.` but never `_`, so `web01.pl`→`web01_pl` and `web01-pl`→`web01-pl` stay distinct), other invalid chars → `-`, strip leading `-`/`_`, truncate 128; `web01.example.com` → `web01_example_com`. `SanitizeGlobDots(pattern)` applies only the `.`→`_` sub to target patterns (shared `peelIDDotSub` const; skips `[...]` class interiors and `\`-escapes — rewriting a `.` range endpoint would widen the class): used by `pkg/target`'s `GlobMatcher` AND `ListMatcher`, the reactor's `MatchRequirePeel` + `NormalizeMatchKeyOrigin` (ONLY the origin segment of match-key globs — tags may legitimately contain `_`), and `enroll approve --peel`, so a dotted target (`web01.pl`) matches the sanitized id everywhere peel IDs are matched. `DisplayPeelID(id)` is the lossless inverse (interior `_`→`.`; empty/`_`-prefixed/invalid ids pass through unchanged) — **the CLI displays peel ids in dotted human form everywhere** (`displayPeel` helper in `cmd/zester/cmd/output.go`; the token form stays valid input). `_` in an id is RESERVED as the wire encoding of `.`: `ResolveNodeID` rejects a configured id containing a raw `_` (write the dot — it round-trips). `config.ResolveNodeID(explicit, cacheDir, log)` wraps `SanitizePeelID`: explicit id (sanitized, never pinned) else the pin at `<cacheDir>/node-id` else `hostname -f` — a derived id is PINNED to that file (Salt minion_id semantics: DNS-degraded `hostname -f` must not re-identify the node across boots; delete the file to re-derive) and localhost placeholders (`localhost`, `localhost_localdomain`, …) are refused. Used by BOTH `cmd/zester-peel` (empty `id` → hostname) and `cmd/zester-watchdog` so peel and watchdog always agree on identity (and the `<id>.creds` filename). `HandlerConfig.OnPending` fires synchronously per NEW pending record (masterd wires the `_master` enroll-pending event). Also owns the **discovery + trust ladder** (`trust.go`, `bootstrap.go`, `verify.go` trust-binding): `ResolveTrust` (enroll_ca file > pin > persisted anchor > system > TOFU, first-contact-only, bundle-poisoning-proof pin anchoring), `BootstrapDoc` + `GET /api/v1/enroll/ca`, `SignTrustBinding`/`VerifyTrustBinding` (fingerprint binding), `Store.ApproveForce`. ## Two-Layer Module Architecture (Execution + State)

Modeled after Salt's execution/state split: **execution layer** (`pkg/exec/`) — stateless imperative provider interfaces + platform implementations, reusable across state modules; **state layer** (`pkg/state/modules/`) — thin idempotent wrappers (Check → Apply → Revert) delegating system calls to the execution layer.

- **ModuleContext**: `exec.ModuleContext` is the Go equivalent of Salt's `__salt__` + `__grains__` + `__pillar__`. It **embeds `ProviderSet`** (field promotion keeps `mctx.Package`-style selectors compiling; composite literals must nest: `exec.ModuleContext{ProviderSet: exec.ProviderSet{File: f}}` — adding a provider touches only ProviderSet/DetectProviders/interface/fake). The peel builds one immutable template (`Agent.mctxTemplate`, frozen after `RenderTemplate` is set) at startup and derives per-request copies via `WithFactsSettings(facts, settings)` — a shallow copy sharing ProviderSet/Logger/RenderTemplate, never mutating the receiver. Mutating executions serialize on the single exec worker behind `execMu`; the read-only set runs concurrently on derived contexts.
- **Provider detection**: `exec.DetectProviders(facts, logger)` selects providers from `os.family` in local facts; called once in the peel's local startup phase (`internal/peeld/agent.go`).
- **Dependency injection**: closure-based builder factories — `NewPkgInstalledBuilder(mctx *exec.ModuleContext) state.Builder` captures the ModuleContext and returns a `state.Builder` using `mctx.Package` internally. `Builder`, `State`, `Registry`, `Runner`, `DAG` are unchanged by this pattern.
- **Provider constructors**: package providers receive `CommandExec` (e.g. `NewAptProvider(cmdExec)`) — they shell out to package-manager CLIs via the injected `CommandExec`. No circular dependencies.

## Requisites & Generic State Attributes

States declare dependencies via `Reqs() Requisites`. `Requisites` has four fields: `Require`, `Watch`, `OnChanges`, `OnFail` (all `[]string`); `AllDeps()` returns the deduplicated union — used by the DAG for ordering edges.

`ParseRequisites(config map[string]any)` extracts the four types from a state config map. Supports string format (`"pkg.installed:nginx"`) and Salt-style dict format (`{"pkg": "nginx"}` — shorthand resolves via `saltShorthandMap`: pkg→pkg.installed, file→file.managed, service→service.running, cmd→cmd.run, user→user.present, group→group.present; unknown modules pass through).

Runner `resolveRequisites()` semantics per state: **Require** — any failed dep → skip (`require_failed`). **Watch** — any failed dep → skip (`require_failed`); any changed dep → `forceApply=true` (skips Check, straight to Apply). **OnChanges** — any failed dep → skip; none changed → skip (`onchanges_not_met`). **OnFail** — none failed → skip (`onfail_not_met`). In ModeRevert, only require-failure propagation applies.

Compile-time rewrites (`transformRequisites()` in `pkg/state/compiler/requisites.go`, after merge/extend, before building):
- **`listen`** aliases to `watch` on the same state; `listen_in` injects `watch` onto its target. Zester runs watch-triggered applies during the run (not deferred to the end); the apply-on-change effect matches Salt, only timing differs.
- **`_in` inverses** — `require_in`, `watch_in`, `onchanges_in`, `onfail_in`, `listen_in`, `prereq_in`: A declaring `<req>_in: [B]` has the key dropped and the *forward* requisite (referencing A as `module:id`) injected onto B.
- **`prereq`** — A declaring `prereq: [B]` gets `require: [A]` injected onto each target B (A ordered before B); A keeps `prereq` for the runtime gate.

**prereq runtime gate** (ModeApply/ModeCheck): a state with prereq targets (via the `Prereqer` interface) calls each target's `Check`: if at least one would change, the state runs with `forceApply=true`; if none would, it's skipped with SkipReason `prereq_not_met`. Missing targets or Check errors are logged and count as "would not change".

Generic attributes (`pkg/state/attributes.go`): `ParseStateAttributes(config)` recognizes `onlyif`, `unless`, `order`, `retry`, `failhard`, `prereq`; `WrapAttributes(inner, attrs, guards)` decorates (returns `inner` unchanged when attrs are zero; embeds the inner State so `Name()`/`Reqs()` pass through). The compiler applies it in `buildOne()` to every compiled state; the peel exec handler applies it to ad-hoc runs — **individual state modules never parse these keys**.

- **onlyif / unless** — shell guards via `GuardRunner` (peel wires its `CommandExec`; nil runner = guards always satisfied). `onlyif`: ALL commands must exit 0 to run. `unless`: skipped if ANY command exits 0. Guard-not-met is a **no-op**, not an error: Check/Apply report no change with diff `"skipped: guard condition not met"`. Guards run before both Check AND Apply (Apply too — watch-forced applies bypass Check). The peel's `runGuard` (`internal/peeld/agent.go`) EXTRACTS the exit code from `CommandExec.Run`'s exit-status error — a non-zero exit is the guard's ANSWER (skip/run), never an error; only context death or spawn failure (ExitCode -1 / no result) errors.
- **order** — int, or `"first"` (−1000000) / `"last"` (1000000). Sorts states *within* a DAG level (lower first, name tiebreak); no order = 0. Never overrides requisite edges.
- **retry** — bare int (`retry: 3`) or Salt map (`retry: {attempts: 3, interval: 10}` — interval in **seconds**, default 10s). Retries on error; only in apply/revert modes, never check/test.
- **failhard** — truthy; on failure all remaining DAG **levels** are skipped with SkipReason `failhard_abort` (same-level states still complete).
- **names** — `ParseNameList()`; compiler expands a `names:` list into one state per name, each using the name as state ID and `name` param (so requisites can target it by name).

**Dry runs**: `state.ModeTest` is an alias for `ModeCheck` (`pkg/state/runner.go`). Triggered by CLI `--test` or a `test=True` module arg (`isTestArg` accepts bool `true` or truthy strings true/yes/1/on, case-insensitive); `ExecResponse` carries `Test: true`.

## Go Filename Convention

**Do not** name files `*_js.go`, `*_linux.go`, `*_darwin.go`, `*_amd64.go`, etc. unless you intend a build constraint — Go treats `_GOOS`/`_GOARCH` suffixes as implicit build tags. Example: `fake_js.go` was silently excluded on `darwin/arm64` (`_js` = `GOOS=js`, WebAssembly).

## Codec & Protocol Versioning

All NATS messages are MessagePack via `bus.Encode()`/`bus.Decode()`; struct tags `msgpack:"field_name"`.

Wire evolution is **additive-only** (normative policy in `pkg/proto/doc.go`): never rename/retype/remove a msgpack field (retired keys stay reserved forever); new fields MUST be `,omitempty` with zero values safe for old AND new readers. `pkg/proto.ProtocolVersion` (currently 1, `version.go`) is the wire-protocol generation — senders stamp it into the `V` fields (msgpack `v,omitempty`) on `ExecRequest`/`ExecResponse`/`Job`; decoded `V == 0` means never set and MUST be treated as compatible. Bump `ProtocolVersion` only for semantically breaking changes; rollouts gate on it via `update.Manifest.MinProtocol` vs the fleet's reported `NodeStatus.Protocol`. Peels also publish a `protocol_version` fact.

## NATS TLS

`tls://` URLs are mandatory everywhere: `bus.ValidateTLSNATSURLs` rejects non-`tls://` URLs on master, peel, and watchdog. Defaults: `tls://nats:4222` (master/peel), `tls://localhost:4222` (watchdog, packaged configs). CA resolution order in `bus.NATSClientTLS`: explicit `--nats-ca` flag / `nats_ca` YAML → `NATS_CA_FILE` env var → `/data/auth/nats-ca.crt` if present → system trust store.

## Multi-Master Coordination (Leader Leases)

`bus.LeaderLease` is advisory leader election over a TTL'd KV entry in the `leases` bucket (15s TTL / 5s renew — bucket TTL must match; `IsLeader` may be stale up to one TTL, so holders must tolerate brief dual ownership). Masters run two leases:

- **`"publisher"`** — gates settings-files, state-files, and reactor-files publish + the GitFS sync loop. The holder keeps on-disk edits flowing live: an fsnotify **file watcher** (`files_watch`, default on; skips hidden dirs relative to each watched root; ~1s debounce) plus a **republish ticker** (`files_republish_interval`, default 30s, the NFS/missed-event backstop) re-run the publishes, all **hash-gated** (manifest byte-equal ⇒ nothing written, no `_revision` bump, no peel churn; `statefiles.Publisher.Publish/PublishForce`, `settings.PublishRawFiles/Force`). The gate additionally verifies **integrity** (`gateIntegrityOK` in both publishers): the `_revision` KV-entry revision must be newer than `_manifest`'s (a publish torn between manifest and bump would otherwise be pinned forever) and every listed key must exist (dual-leader prune casualty) — violations fall through to a repairing publish. **Under GitFS, states publishing belongs to GitFS alone** (its clone-validity gate must never be bypassed): `publishStateFiles` returns `Skipped:"gitfs-managed"` and the watcher doesn't watch the states root. `zester fileserver update [--force]` (`zester.admin.fileserver.update`; plain-subscribed on every master, ONLY the holder replies — silent non-holders, so a timeout means "no holder") triggers publishes on demand; `--force` bypasses the hash-gate (tamper-heal). Settings publish RE-READS the dir, refreshes `rawSettingsFiles`/`allSecrets`/`topFile` under `settingsMu`, and on an extracted-secrets fingerprint change fans re-encryption out to the whole facts index (`republishSecretsToFleet` — a rotated `!encrypted` VALUE is hash-gate-invisible and stable peels' facts publishes hash-skip, so nothing else would deliver it; per-peel `PublishSecrets` stays hash-gated). **Standby mirror** (`files_mirror`, default on; `internal/masterd/mirror.go`): a master not holding the lease ~2 TTLs after boot OR after a loss (OnLost re-arms the same timer — never an instant mirror, so a NATS-blip re-acquisition can't race it) mirrors states, settings, and reactor KV→dir via the generalized `statefiles.Cache` (`reactor/` prefix + WarnLocalEdits; mirrored dirs are MANAGED trees — unpublished extras don't survive). **Settings converge through the SEALED masters-only `master-settings` bucket, never the sanitized peel-facing one** (a sanitized mirror would destroy `!encrypted` plaintext): the holder publishes the RAW tree with each file sealed to the shared account curve key (`PublisherConfig.EncodeValue`) and the manifest hashed with account-seed HMAC (`PublisherConfig.HashValue` = `masterSettingsHash`; keyed so a `$KV.>` reader can't brute-force secret VALUES offline, deterministic so the gate holds). Published FIRST, from the SAME file set as the sanitized publish (`publishSettingsFiles` calls `publishSealedSettings(files)` before `PublishRawFiles`), so an interruption rolls FORWARD not backward on failover. The standby opens on sync (`CacheConfig.DecodeValue`+`HashValue`) and `OnSynced` → `refreshSettingsStateFromDisk` re-extracts secrets; a periodic `runStandbySettingsRefresh` (30s) covers files_mirror=false shared-volume masters too (in-memory state would otherwise stay boot-stale). The fleet re-encryption fan-out (`republishSecretsToFleet`) runs async (not under the mirror's syncMu). `master-settings` is History:1 (old sealed ciphertext must not linger post-rotation). Grants: peel JWTs have NO `master-settings` entry; admin creds read ciphertext + keyed hashes only (no `account.seed`); the sealed publish is skipped when `files_mirror` is off. Takeover = stop mirror (Quiesce) → catch-up sync (only if the mirror synced this lifetime — a fresh boot that wins immediately publishes its OWN tree, preserving single-master offline-edit semantics) → hash-gated no-op publish; the fleet never reverts to a stale states/reactor tree. `startFilesMirrors` re-checks leadership under `mirrorMu` (timer-vs-acquisition race). GitFS-sourced states auto-excluded; disable on shared-volume masters (compose does). Leadership surfaces: `publisher-lease` readyz entry (informational), `zester_master_publisher_leader` gauge, `<publisher_status_file>` (default `/run/zester/publisher-status`, MOTD snippet in the master deb), `zester fileserver status` (holder self-reports hostname; CLI hints on `nats.ErrTimeout` too).
- **`"facts-secrets"`** — gates only the `PublishSecrets` call in the facts watcher (enrollment `MarkActive` stays ungated), so exactly one master reacts to facts churn with re-encryption.

Up to one TTL (~15s) of dual publishing during partitions is tolerated by design — all gated writes are idempotent Puts and/or hash-gated. On lease handover the new leader re-runs the full publish, which the hash-gate turns into a no-op when its mirrored dirs already match published truth.

## Target Resolution Service

Master-side request/reply service over an in-memory facts index — replaces O(fleet) full-facts-bucket scans for targeting and `basket()`. Every master maintains a `facts.Index` via `facts.WatchIntoIndex` and serves `target.StartResolveService` on `zester.target.resolve` (QueueSubscribe, default queue `DefaultResolveQueue` = `"zester-target-resolvers"` — one master answers each request; runs on all masters, not lease-gated; `IndexResolveFunc`/`IndexLister` over the index). Wire: `ResolveRequest{expr, type, want_facts}` → `ResolveResponse{peels, facts, err}` (msgpack, additive). Clients — CLI job mode and the peel's `basket()` — wrap their KV lister in `target.NewServiceLister(ps, 5*time.Second, fallback, logger)` (client-side `PeelLister` + `BulkPeelLister` + `ExprResolver`): `target.Resolve` delegates whole expressions to `ExprResolver` listers first, so only matched peel IDs cross the wire; ANY failure (no responders, timeout, decode/remote error) Warn-logs (`"target: resolve service unavailable, falling back to facts KV scan"`) and retries via the wrapped fallback — mixed-version fleets degrade to the scan path. `ServiceBasketQuery` is the WantFacts variant (no built-in fallback). `--direct` keeps the pure KV lister. The master's `target-service` readiness check is Down until the service starts (startup failure non-fatal).

## Job System

- CAS-protected ownership via KV (`jobsBucket.Create` for idempotent dispatch, `jobsBucket.Update` for fencing); each master has a unique KSUID-based `masterID`.
- `Job` carries `Deadline`, `ReclaimCount`, `StateID`, `User`, `TargetExpr`, `V`, `ReturnCount`/`SuccessCount` (set at finalize), `Epoch` (CAS-bumped on every legitimate redispatch).
- **JID-collision semantics** (`Manager.Dispatch`): own still-claimed record → resume (checked BEFORE the intent comparison, so reactor re-renders with drifted args still resume); another master's still-claimed record → `ErrJobClaimPending` (typed, retryable — a claimed record is provably never-published and its live owner may never resume it; the reactor Naks it as transient); past-claimed + same intent → idempotent nil; past-claimed + different intent → `ErrJIDConflict` (the reactor classifies THAT as duplicate-suppressed on its content-addressed `rxn-` JIDs).
- `MetadataReactorDepth` (`"reactor_depth"`) → `ExecRequest.ReactorDepth` on ALL publish paths. Watcher ack/return identity is the subject token; a payload `PeelID` mismatching it is dropped as forgery.
- **Active-jobs index**: the jobs bucket holds two key families — `<jid>` (msgpack `Job`) and `active.<jid>` (`job.ActiveJobKeyPrefix`; msgpack `ActiveJobEntry{owner, updated}`). Dispatch Creates the active key right after the job record; the orphan scanner enumerates ONLY `bus.ListKeysWithPrefix(jobsKV, "active.>")` — O(active jobs), independent of the 7-day retention — rewrites the key on reclaim, and self-heals stale keys (missing or terminal job record → delete + skip). The key is deleted on every terminal transition (Warn-only on failure; a CAS-fenced finalize deliberately leaves it for the superseding owner/scanner). Scheduler-synthetic jobs never get index entries.
- **Dispatch ordering invariant**: Create(claimed) → active key → dispatch event → CAS to `StatusRunning` → publish ExecRequests → start watcher. A CAS-to-running failure returns an error WITHOUT publishing, so `StatusClaimed` in KV provably means never-published — reclaiming a claimed job re-dispatches safely by construction (same CAS-before-publish inversion on `ReclaimJob`'s claimed path). A retried Dispatch of an own interrupted claim resumes from the running-CAS step and publishes exactly once relative to KV state.
- `Job.Deadline` (msgpack `deadline,omitempty`) is ALWAYS re-anchored by the master in `Manager.Dispatch` (client clocks untrusted). Recovered watchers honor the remaining budget; an expired deadline finalizes immediately from collected returns; a zero deadline is normalized to `Created + Timeout` (`normalizeDeadline`) before use.
- `Job.StateID` (msgpack `state_id,omitempty`) carries the CLI's bare positional (e.g. `zester '*' pkg.version nginx` → "nginx"), forwarded as `ExecRequest.ID` — job mode behaves like `--direct`.
- `Job.User` from operator identity (os/user → `$USER` → "unknown"); shown in `zester job list`/`job active` (USER column) and `job show` JSON. `Job.TargetExpr` is audit-only, never interpreted by pkg/job. `Job.V` stamped from `proto.ProtocolVersion` by `NewJob`. The master Info-logs every accepted dispatch with jid, user, function, target count. `--direct` bypasses job records entirely (unattributed).
- **Per-peel returns are the source of truth**: the watcher persists each return to `"<jid>.<peelID>"` via a buffered channel (256) + dedicated writer goroutine (synchronous-persist fallback on overflow — never drops; guaranteed drain before finish/detach/finalize; failed writes re-queued). `finalizeJob` writes no aggregated value — the job record carries `ReturnCount`/`SuccessCount`; `GetReturns`/recovery list per-peel keys via `bus.ListKeysWithPrefix` — per-peel keys are the ONLY returns storage (scheduled results included).
- **Ack + re-dispatch reconciliation**: peels publish `job.Ack` (msgpack) on `bus.JobAckSubject(jid, peelID)` when ACCEPTING a dispatch — after epoch/dedup fencing, before execution. Dispatch watchers re-publish the ExecRequest exactly ONCE (same Epoch) to targets that neither acked nor returned within `Manager.AckWindow` (default `DefaultAckWindow` = 5s; negative disables) — safe because peels dedup on persisted jid→epoch (an acked-but-slow peel is never re-sent). Recovery watchers never re-dispatch.
- **Reclaim replays the durable stream**: reclaiming a running job replays the `job-events` stream for that JID (`NewStreamReturnReplayer`: ephemeral pull consumer, DeliverAll, read-until-idle, subject-token-authoritative peel identity; auto-wired in `NewManager` when the JetStreamAPI also implements `bus.ConsumerAPI`) TWICE — before the recovery watcher starts (seeding; KV-persisted returns win on collision) and again after live subscriptions attach (`Watcher.Subscribed` + `MergeReturns`) — a return published in the replay→subscribe gap isn't lost. Seeds covering all targets finalize immediately.
- Heartbeater writes to the `master-heartbeat` bucket (TTL 15s, interval 5s). `ListLiveMasters` returns real KV errors (empty bucket ≠ error); a per-key heartbeat read error aborts the scan — only key-not-found (= expired) counts as dead.
- OrphanScanner aborts the whole cycle on liveness errors; reclaims via CAS only after an owner is absent for `MissThreshold` (default `DefaultMissThreshold`=2) consecutive scan cycles — reclaim latency ~heartbeat TTL + 2×20s scan cycles (~55s worst case). `Job.ReclaimCount` (msgpack `reclaim_count,omitempty`) increments per reclaim; after 3 reclaims (`maxReclaims`) the job is CAS-finalized failed (`Metadata["failed_reason"]`) instead of re-dispatched.
- Metric hooks: `Manager`/`Watcher.OnJobFinalized(function, status, duration)` fires on every finalize (not on CAS-fenced finalizes or shutdown detach); `OrphanScanner.OnReclaim` fires per reclaimed job.

### Scheduler Returns (return_job)

Peels never write to the `jobs`/`job-returns` KV buckets. A schedule entry with `return_job: true` publishes a `job.ScheduledResult` (msgpack) on the peel-scoped subject `zester.job.<jid>.schedule.<peelID>` (`bus.JobScheduleSubject`, `pkg/job/schedresult.go`); the `job-events` JetStream stream captures it durably (7-day retention), surviving master downtime. All masters share the durable consumer `schedule-results` (`job.StartScheduledResultConsumer`, filter `bus.JobScheduleWildcard()`), which persists the synthetic job record (idempotent `jobsBucket.Create`, metadata `source: schedule`) plus the per-peel return. The reporting peel's identity comes from the NATS-permission-enforced subject token, never the payload: peel JWTs (`auth.PeelUserJWTOptions`) allow publishing only `zester.job.*.schedule.<peelID>` (and `zester.job.*.ack/return.<peelID>`) and carry no `$KV.jobs`/`$KV.job-returns` grants — one compromised peel cannot read, forge, or overwrite other peels' job records or returns.

### Peel Heartbeat & Presence

Peels Put `facts.Heartbeat{ts, version, protocol}` under `<peelID>` into the `peel-heartbeat` bucket (`bus.BucketPeelHeartbeat`, TTL 30s, history 1) every 10s from the connected phase; failures Debug-logged, retried each tick. Offline after ~3 missed beats. `zester peel list` derives ONLINE/LAST-SEEN from the bucket; the master feeds `zester_connected_peels` from bucket key counts every 15s. Authorized by the peel JWT's `$KV.peel-heartbeat.<peelID>` grant.

## Reactor & Events (Event-Driven Automation)

Salt-style reactor: events publish under `zester.event.>` (msgpack `event.Event`), captured durably by the `events` JetStream stream (7d, 1 GiB, 1M msgs, MsgID dedup window 2m); the masters' shared durable consumer `"reactor"` (DeliverNew, AckWait 60s, MaxDeliver 5, MaxAckPending 64) delivers each event to exactly ONE master — no reactor leader, capacity scales with masters, downtime replays from last ack.

- **Identity is the subject token**, never the payload: peel JWTs allow publishing only `zester.event.<own-id>.>`; the payload `tag` is cross-checked against the subject-derived tag (mismatch = spoof drop); `enroll.ValidatePeelID` bans dots/leading-`_`/wildcards so peel origins can never collide with `_master`/`_admin`. Rules match `"<origin>/<slashTag>"` keys (`event.MatchKey`) — a compromised peel can only spoof itself.
- **Rules**: `reactor/top.zy` — plain YAML, ordered single-key entries, bare-list or `{react, throttle}` options form; fnmatch match-key globs where `'*'` crosses `'/'`; ALL matching rules fire in file order. Distributed via the master-only `reactor-files` bucket (files → `_manifest` → `_revision`; publisher-lease-gated; empty dir never wipes a populated bucket); the loader verifies SHA-256 against the mandatory `_manifest` (content-without-manifest = torn publish), hot-reloads on `_revision` (debounced 2s + 5s jitter), atomic snapshot swap, keeps last-known-good on ANY load failure (degraded `reactor` readiness + `zester_reactor_rule_errors_total`), emits enroll-lint warnings.
- **Rendering** (`render.go`): Jinja-rendered reaction `.zy` files with `ModuleFn=nil` — `salt[...]` is a render error; context `event.{id,tag,peel,origin,depth,ts,data}` + aliases `tag`/`data` + `origin_facts`. Actions normalized + post-render validated (function must match `^[a-z0-9_]+\.[a-z0-9_]+$`, target must parse, `max_targets`); one invalid block = NO actions execute. Actions: `dispatch.module`, `dispatch.state` (sls/highstate), `local.*` Salt sugar, `enroll.approve/reject/revoke`, `event.send` (chaining; deterministic `DeriveChainID` + JetStream MsgID dedup; refused at depth cap or when chaining disabled), `log`.
- **Exactly-once side effects** on at-least-once delivery: reaction JIDs are content-addressed (`rxn-<sha256(origin,eventID,rule,block)>[:32]`; `job.ErrJIDConflict` → duplicate-suppressed) with provenance metadata; derived events get deterministic IDs published with JetStream MsgID; enroll transitions dedup in the state machine. Consume-gate order: malformed→decode→spoof→depth→ratelimit→stale (all Ack+drop+metric; stale Warns loudly). Worker pool (default 4) with 30s render timeout, panic recovery, InProgress keepalive; Ack only after all matched rules complete or fail permanently; NakWithDelay on transient failures/backpressure.
- **Loop guards** (chaining is ON by default — correctness-critical): depth cap 3 (`Event.Depth`, propagated through reaction jobs via `Job.Metadata["reactor_depth"]` → `ExecRequest.ReactorDepth` → peel `event.send`); per-source token bucket rate limit (120/min burst 30, LRU-bounded); per-(rule,source) throttle; per-rule storm breaker (60/min → open 5m). Throttle and breaker are TWO-PHASE — checked before a rule executes (`Throttle.Allow`/`Breaker.Allow`), recorded only after non-transient completion (`Throttle.Record`/`Breaker.RecordFire` in `engine.process`) — a transiently failed attempt never consumes guard state and its Nak redelivery retries. `Breaker.Sweep`/`OpenRules` (surfaced as `Engine.SweepBreakers`/`OpenBreakers`) close expired cooldowns without a new event; the master's lag-gauge loop (15s) also sweeps breakers and feeds the breaker-open readiness/gauge.
- **Staleness gate**: default 1h — a longer full-master outage DROPS queued events with a loud Warn + `reason="stale"` metric; `max_event_age: 0` = full replay.
- **Enroll actions are double-gated**: `require_peel` glob is compile-mandatory AND the executor refuses non-`_master`-origin events. Reaction jobs carry `User "reactor:<rule>"` + `Metadata{source: reactor, rule, event_id, event_tag, reactor_depth}`; reactor-actioned enrollment records carry operator `"reactor"`.
- **Dry run**: `zester.reactor.test` request/reply service (queue `zester-reactor-testers`, `service.go`), used by `zester reactor test`.
- **Config**: master `reactor.*` section (enabled default true, dir `/data/reactor`, workers 4, max_chain_depth 3, enable_chaining true, default_throttle 0, source_rate_limit 120, max_event_age 1h, storm_rate 60, breaker_cooldown 5m). Config `0` = disabled is translated to the pkg convention (negative = disabled / 0 = default) by `gateInt`/`gateDuration` in `internal/masterd/reactor.go`; duration knobs are `config.Duration` — YAML accepts time.ParseDuration strings AND bare `0`, which plain time.Duration fields reject — bound as ordinary duration flags by `bind.go`.
- **Producers**: peel `event.send` module (mutating-queue path, bare positional = tag), `pkg/beacon` service beacon, `zester event send` (`_admin`), master enroll-pending hook + reactor `event.send` chains (`_master`; chained events match under `_master/reaction/<tag>`).
- **Phase 2 (NOT in v1)**: full beacon set (disk/mem/load/filewatch), master job-lifecycle events (`job/<jid>/finalized`), `runner.orchestrate`, `wait_for_returns`, zester-migrate reactor-SLS conversion.
- Docs: `website/content/docs/architecture/reactor.mdx`, `guides/reactor.mdx`, `operations/reactor.mdx`, `reference/events.mdx`.

## Settings Pipeline

Two-phase rendering:
1. **Master side**: sanitizes `.zy` files (replaces `!encrypted` values with `__ZESTER_SECRET:key__` placeholders), publishes to shared KV (files → `_manifest` → best-effort stale-key prune → `_revision` bump; publisher-lease-gated), encrypts secrets per-peel (hash-gated, `facts-secrets`-lease-gated).
2. **Peel side**: Resolver loads raw files from KV, verifies against the `_manifest`, evaluates `top.zy` targeting, renders templates with local facts, decrypts secrets.

Resolver / publisher hardening:
- **Manifest verification**: `_manifest` (`settings.ManifestKey`, sorted msgpack `[]ManifestEntry{key, sha256}` of the stored bytes) — top.zy and every matched file must be listed with a matching hash; listed-but-missing, hash mismatch, and loaded-but-unlisted all FAIL the resolve (torn-read protection, never cached). The manifest is mandatory: settings content without a `_manifest` fails the resolve as a torn or tampered publish; an absent manifest is legitimate only before the master's very first publish (resolves to empty). Publish order (`PublishRawFiles`): files → `_manifest` → best-effort prune of stale keys (never `_revision`/`_manifest`/`_master_curve_pub`; prune failures Warn, never block the `_revision` bump — unlisted keys are inert because loading is manifest-selective) → `_revision` bump.
- **Revision sampling**: `Resolve` samples `_revision` at entry and re-reads it at cache-write time, caching only when both match (and the invalidation generation is unchanged) — a publish landing mid-resolve can never pin the old batch under the new revision.
- `Resolver.Resolve` FAILS (never caches) when unresolved `__ZESTER_SECRET:...__` placeholders survive the final merge — states are never applied with placeholder strings.
- Secrets rotation applies without a settings-files revision bump: the peel's secrets-watch callback calls `resolver.InvalidateCache()` before the debounced re-resolve; an invalidation-generation counter prevents an in-flight resolve from re-caching pre-rotation values.
- **Secrets hash-gate**: `PublishSecrets` keeps a per-peel fingerprint cache (SHA-256 of sender curve pub ‖ recipient curve pub ‖ length-prefixed sorted secrets) and skips the randomized re-encrypt + KV put when unchanged (cache updated only after a successful put; `InvalidateSecretsCache` drops entries); only the `facts-secrets` lease holder reacts to facts updates.
- **Snapshot warm-start**: the peel persists last-known-good resolved settings to `/data/settings-snapshot.msgpack` (0600, atomic rename, hash-gated) on every successful resolve and loads it at boot to warm `cachedSettings`, `basket_scope`, and the scheduler — offline boots enforce with snapshot settings.
- Peel exec path fails closed: on exec-time resolve error, `state.apply`/`state.highstate` fall back to last-known-good `cachedSettings` (Warn); if the peel has never resolved successfully (not even from the snapshot), the execution FAILS with an explanatory `ExecResponse` error. States are never applied with nil settings.
- Settings re-resolution runs on the peel's serialized exec-worker path (template rendering can invoke execution modules via `salt['mod.func']`); template-invoked module calls are bounded by the 60s `moduleDispatchTimeout`.

## Basket Scope

Query-side filtering for multi-cluster basket isolation via the `basket_scope` setting (e.g. `basket_scope: "G@cluster_name:{{ facts.cluster_name }}"`). The peel's `makeBasketFunc` (`internal/peeld/basket.go`) takes a `scopeFn func() string`; when non-empty it compound-ANDs the scope with the caller's target using parentheses — `"(" + tgt + ") and (" + scope + ")"` — so `a or b` targets cannot bypass it. The scope lives in a `sync.RWMutex`-protected variable, seeded from initial settings resolution (or the snapshot), refreshed on settings changes. Resolution goes through the master resolve service via `target.NewServiceLister` (IDs-only) with automatic facts-KV-scan fallback.

## Enrollment System

Manual-approval enrollment for new peels — challenge-response HTTP API on the master replaces out-of-band `.creds` distribution.

- **HTTP API (peel-facing)**: `GET /api/v1/enroll/nonce`, `POST /api/v1/enroll`, `GET /api/v1/enroll/{id}/status`, `GET /api/v1/enroll/{id}/creds`. TLS mandatory — `NewServer()` refuses startup without cert/key (default `/data/auth/enroll.crt`, `/data/auth/enroll.key`). The same TLS listener mounts the token-authenticated REST API via `enroll.ServerConfig.ExtraRoutes` (see `pkg/masterapi`).
- **CLI (admin ops)**: `zester enroll list [--state]|show` read the enrollments KV directly; `approve|reject [--reason]|revoke [--reason]` send an `enroll.AdminRequest` over NATS request/reply (`bus.SubjectAdminEnrollApprove/Reject/Revoke`, 5s timeout), answered by the masters' `zester-masters-admin` queue group (`internal/masterd/admin.go`, Info-logs id+operator+action). Persistent `--direct-kv` flag = break-glass direct-KV write with the operator's NATS creds (for when no master runs; a no-responders error hints at it). List/approve/reject/revoke also available over the REST API (bearer tokens).
- **Peel client**: auto-enrolls when no `.creds` file exists; challenge-response + status polling with exponential backoff (10s..5m). Multi-URL failover via `enroll.ClientConfig.MasterURLs` (peel `master_urls`): rotate on connection-level failures/5xx across all operations (nonce, submit, status poll/SSE, creds download), pin the URL on success, never rotate on 4xx; a 401 "challenge verification failed" transparently re-requests a fresh nonce and resubmits (3 total attempts).
- **KV buckets**: `enrollments` — records keyed by enrollment ID (`enr-<KSUID>`) + peel index (`peel.<peel-id>`), no TTL, 10 history (`BucketEnrollments`); `enroll-challenges` — nonces keyed `chl-<KSUID>`, 5-minute TTL, 1 history (`BucketEnrollChallenges`).
- **State machine**: 6 states — `pending` → `approved` → `issued` → `active` → `revoked`, with `rejected` branch from `pending`; revoke also valid from `approved`/`issued` (`validTransitions` in `pkg/enroll/enrollment.go`).
- **Security**: Ed25519 challenge-response — peel signs `nonce || curvePublicKey`, binding both Ed25519 and X25519 keys (prevents curve key substitution). Unenrolled peels have ZERO NATS access — only the enrollment HTTP API over TLS 1.3. Private nkey seed generated locally on the peel, never transmitted; credential download requires a second Nkey signature of the enrollment ID; creds stored 0600. Admin ops split by transport: operator NATS creds carry `zester.admin.>`; day-to-day admin needs no enrollments-bucket write access (only `--direct-kv` does); peel JWTs must never get the admin grant. Peel index `peel.<id>` written first via `kv.Create` as atomic uniqueness guard (no duplicate enrollments under concurrency). Per-IP token-bucket rate limiting split by path: strict for `/api/v1/enroll` + subpaths (burst 10, 1 req/10s); all other routes on the listener (the REST API) get burst 120, 20 req/s. CAS concurrency control for multi-master safety.
- **Tests**: `package enroll_test` with `bustest.NewFakeJS()` + real nkeys — state machine, store CRUD with CAS, challenge lifecycle, signature verification (incl. curve key binding), HTTP handlers via `httptest`, credential issuance, admin round-trips, file persistence.
- **Docs**: `website/content/docs/architecture/enrollment.mdx`, `operations/enrollment.mdx`, `reference/enrollment-api.mdx`, `architecture/enrollment-design.mdx`, `architecture/enrollment-security.mdx`. Docs site: Fumadocs (Next.js) in `website/` — MDX content in `website/content/docs/`, nav in `meta.json` files, deployed to GitHub Pages by `.github/workflows/docs.yml` (static export, `DOCS_BASE_PATH=/zester`).

## Embedded CA & Zero-Config Bootstrap

Optional mode where the master IS the CA (Puppet-style), so a peel is provisioned with just `master_urls` (+ an optional `enroll_ca_pin`) — the NATS endpoint list and CA trust bundle are discovered at enrollment and cached locally. NATS is NEVER embedded; the master only serves metadata about the external server. Docs: `website/content/docs/{operations,architecture}/embedded-ca.mdx`, `reference/ca-cli.mdx`.

- **CA (`pkg/ca`)**: `zester ca init` (offline) generates a root + signing-intermediate (`<auth_dir>/ca/{root,intermediate}.{crt,key}`) and prints the root SPKI pin. Trust distribution uses the ROOT only (peels pin/anchor the root; servers present leaf+intermediate chains), so intermediate rotation never touches peel anchors. Leaves carry dual ServerAuth+ClientAuth EKU and are clamped to the intermediate's validity. Multi-master: replicate the CA dir like `account.seed` (NOT via KV).
- **Master mode** (`ca.mode: auto|embedded|external`, default auto = embedded iff `<ca-dir>/root.crt` exists; `internal/masterd/ca.go`): embedded self-issues the enrollment HTTPS leaf from the CA and hot-renews it in-process (`GetCertificate`, renewal retries hourly on failure), so `enroll.tls_cert/key` are unused. New `ca` readiness check (down/degraded on leaf OR chain expiry). Absent CA material in explicit `embedded` mode is fatal.
- **Discovery** (`internal/masterd/discovery.go`): master `nats_advertise_urls` (`[]string`) → served at unauthenticated, cacheable `GET /api/v1/enroll/ca` as a JSON `enroll.BootstrapDoc{v, ca_bundle_pem, fingerprint, nats_urls, issued_at}`, and republished to the `_cluster_info` secrets-KV key (peel JWT gains `$KV.secrets._cluster_info` read). `bus.ValidateAdvertisableNATSURLs` enforces tls:// + rejects loopback/unspecified/link-local/`0.0.0.0/8`/localhost(-trailing-dot)/hex-inet_aton — the master's own `tls://localhost` view never leaks. CA fingerprint divergence across masters is warned.
- **Peel trust ladder** (`pkg/enroll/trust.go`, `ResolveTrust`): `enroll_ca` file > `enroll_ca_pin` (SPKI) > persisted anchor `<auth_dir>/enroll-ca.crt` > system trust > TOFU (`enroll_trust: tofu` default | `strict`). **Pins/anchors gate the handshake ROOT only** (`ca.FindPinnedRoot` — bundle-poisoning-proof, never trusts a whole served bundle); a configured pin/anchor that mismatches is FATAL, never a downgrade. TOFU fires ONLY on genuine first contact (no creds); an already-enrolled peel seeing an unknown authority is fatal, never re-TOFU (Salt `minion_master.pub` semantics; break-glass `rm <auth_dir>/enroll-ca.crt`). Config parsed strictly (`KnownFields`) so a typo'd pin fails startup loudly. **The peel persists only the pin/anchor-VERIFIED root as `nats-ca.crt` and re-fetches endpoints over verified TLS** — a correct pin protects the discovery payload, not just the handshake.
- **Fingerprint binding** (`pkg/enroll/verify.go`, `SignTrustBinding`): the peel signs the trusted-CA SPKI into the enrollment submission (`trusted_ca_spki`/`trust_signature`, domain-separated from the pinned `enrollSignatureMessage`, challenge-bound). Embedded-CA masters REQUIRE the binding (a stripped binding is rejected — relay-MITM masquerade closed). The master compares it to its root: `Record.TrustChecked`/`TrustMismatch`; `enroll list/show` TRUST column; `enroll approve` refuses a mismatch without `--force`; reactor auto-approval refuses unconditionally.
- **Peel bootstrap cache** (`internal/peeld/bootstrap.go`): `<data_dir>/nats-bootstrap.msgpack` (JSON) holds the discovered NATS endpoints. Boot precedence: explicit `nats_url` (non-empty) > cache (identity-hashed to `master_urls`+pins) > enrollment discovery > builtin `tls://nats:4222` tail (`nats_url` default is now the empty discovery sentinel). Offline-first from cache. Recovery loop (unhealthy > 5m → re-fetch over verified TLS → `bus.Client.SetServers` = `SetServerPool`+`ForceReconnect`, nats.go v1.52.0) + `_cluster_info` watch repoint the live pool without a restart. All candidate URL lists (fetch/KV/disk) re-pass the loopback validator.
- **Convention master**: no `master_urls` → peel tries `https://zester:8443` (Salt-style, enrollment path only). **A single all-in-one box cannot be zero-config** (the master may not advertise loopback) — keep explicit `nats_url` there.
- **Rotation**: intermediate rotation is invisible to peels; root rollover is a two-phase overlap bundle — a file drop, no process restarts (the per-reconnect `nats.RootCAsCB` re-reads trust). Never rotate during an update-rollout soak window.
- **Packaging/playground**: `zester-peel.service` runs the watchdog with `--bootstrap-cache`; packaged `peel.yaml` is the 2-line zero-config form; `playground-init` issues ONE CA via `pkg/ca` (enroll + NATS share the root, satisfying ENROLL-TLS-3) and the compose master runs embedded mode.

## State Composition (Include / Extend / Highstate)

Salt-style composition via `pkg/state/compiler`:

- **Include**: dot-notation references (`include: [common.packages, webserver.config]`); resolution is depth-first with cycle detection and diamond deduplication (each file loaded exactly once). Dot-notation → path: `"webserver"` → `webserver/init.zy`, `"webserver.config"` → `webserver/config.zy`, `"common.packages"` → `common/packages.zy`.
- **Extend**: modifies included states; requisite lists (`require`, `watch`, `onchanges`, `onfail`) are **appended**, all other keys **replaced** (last-writer wins). Extend can only target states from included files.
- **Merging**: duplicate state IDs (via includes, top file, or `CompileMultiple`) are deep-merged (same semantics as `MergeSettings`), processed in depth-first load order. Requisite lists appended, other keys replaced (later file wins). Same state ID with different modules across files → both kept as separate DAG states (e.g. `pkg.installed:nginx` and `file.managed:nginx`).
- **State top file**: `/data/states/top.zy` maps targeting patterns to state sets (same format as settings `top.zy`); rendered as Jinja2 before parsing.
- **Highstate**: `state.highstate` resolves the state top file for the target peel, compiles all matching states (with includes/extends), applies them. CLI: `zester '<target>' state.highstate` (add `--direct` for direct peel access).
- **Pipeline**: `state.apply "webserver"` → load `webserver/init.zy` → render Jinja2 → parse YAML → extract `include:`/`extend:` → recursively load includes (depth-first) → deep-merge duplicate IDs → apply extends → load Starlark modules from `_modules/` dirs → build `[]state.State` via Registry → `runner.Run()`.

## Starlark Custom Modules

Drop `.star` files into `_modules/` directories within the states tree; they become state modules (Starlark = sandboxed Python dialect). Package `pkg/starmod` (see table).

- **Loading**: peel startup — `Loader.LoadGlobal()` scans `{statesDir}/_modules/`; compile time — the compiler calls `Loader.LoadDir()` for each directory that contained state files (formula-specific). Loader is idempotent (re-loading the same `.star` by absolute path is a no-op); later registrations override earlier (formula overrides global).
- **Function discovery**: a function registers as a module action if it's a `*starlark.Function`, doesn't start with `_` (private helper), and doesn't end with `_check`/`_revert`. Optional `{name}_check`/`{name}_revert` companions provide Check/Revert; without them Check always returns `NeedsChange: true` and Revert is a no-op.
- **Naming**: `{filename}.{function}` — `nginx.star` containing `configured()` registers as `nginx.configured`.
- **Builtins**: `cmd_run`, `file_*`, `pkg_*` delegate to `ModuleContext` providers (same fakes work in tests); `http_*`, `json`, `base64_*`, `hash_sha256`, `sleep`, `log.*` use Go stdlib; `facts` and `settings` are injected as frozen (immutable) Starlark dicts.
- **Compiler integration**: `CompilerConfig.StarLoader` (interface `StarModLoader`, defined in the compiler package to avoid importing starmod) is called in `CompileMultiple()` before `Registry.Build()`; `uniqueParentDirs()` extracts directories from source file paths.

## State File Distribution (KV + GitFS)

State files flow master → peels via NATS KV, mirroring the settings pipeline:

1. **Master publishes** (publisher-lease-gated): `statefiles.Publisher.PublishFiles` walks `--states-dir`, Puts all file keys (raw bytes, not msgpack), Puts `_manifest` (`statefiles.KeyManifest`; sorted msgpack `Manifest{Files: []ManifestFile{key, sha256}}` describing the COMPLETE set), bumps `_revision` (the peel-watched signal), then best-effort Deletes bucket keys absent from the set (never `_revision`/`_manifest`; failures Warn — the manifest is the read-side source of truth, KV deletion is GC). Publishing an empty set over a populated bucket is REFUSED unless `PublisherConfig.AllowEmpty` — a misconfigured empty states dir cannot wipe every peel's cache.
2. **Peel caches**: `statefiles.Cache` debounces revision events (`settings.NewDebouncedFunc`, 2s debounce + 5s jitter defaults) and syncs with capped-backoff retry (1s→30s, ctx-aware) until the bucket's current `_revision` is synced (`Cache.LastSyncedRevision`; concurrent triggers collapse via a lost-trigger-free singleflight). `Sync` is atomic: the complete file set is staged in a fresh sibling temp dir and swapped via rename (live→`.old`, stage→live, remove `.old`; leftover `.old` cleaned next sync) — mid-download failures leave the previous complete tree intact. Fetches EXACTLY the manifest's file set with SHA-256 verification (mismatch = failed attempt → retry), prunes unlisted local files. Manifest mandatory: file keys without `_manifest` = torn/tampered publish, fails the sync (retry loop re-syncs once the publisher completes); an empty bucket (before first publish) is a clean no-op. Path-escaping keys rejected.
3. **Compiler reads**: `compiler.NewCompiler()` uses the cache dir (fallback: baked-in `/data/states`). The peel re-evaluates the dir (`resolveStatesDir`) before every execution, retrying an empty/missing cache dir 5×25ms (covers the atomic-swap window) before falling back (Warn). KV-only peels with no states dir at boot don't crash-loop: the states engine builds lazily on the first execution after state files land; until then `state.apply`/`state.highstate` return a clear "states engine unavailable" error and all other modules work normally.

### GitFS

Optional Git state-file source: master clones repos into `--states-dir` at startup, pulls on interval, republishes to KV after each sync (publisher-lease-gated). Flags: `--gitfs-remotes` (comma-separated remote URLs), `--gitfs-interval` (default 5m), `--gitfs-ssh-key` (SSH private key path). Each remote clones into `{states-dir}/{repo-name}/` (last URL path segment minus `.git`). Clone-vs-pull is decided on repository **validity** (own `.git` entry + anchored `git rev-parse`), not directory presence: an invalid dir (e.g. interrupted clone) is removed and re-cloned (self-healing, Warn). Fresh clones stage into hidden temp sibling dirs (`.<repo>.clone-*`, skipped by the publisher walk, stale ones swept) and `os.Rename` into place — an interrupted clone never leaves a half-populated repo. When a remote's sync fails, the republish proceeds only if that remote's local clone is a VALID repo (last known good); otherwise the whole publish cycle is skipped — a partial clone can never propagate fleet-wide deletions. `--gitfs-remotes ""` (explicitly empty) disables GitFS even when YAML lists remotes (`config.ApplyVisited` re-applies user-set flags after YAML load).

## Self-Update System

Binary self-update via the dedicated watchdog process: operator publishes a binary to NATS Object Store, starts a rollout, the master coordinates fleet-wide batches.

**Two upgrade channels (doctrine, docs `operations/upgrading.mdx`):** the RUNNING binary changes via the self-update plane (rollout, soak+rollback, watchdog-owned slots); packages/config align via apt or the `pkg` module. The `.deb` `prerm` (`packaging/scripts/preremove-*.sh`) acts ONLY on `prerm remove`, never `prerm upgrade` — dpkg runs prerm on upgrades too, and stopping the unit from inside its own cgroup (e.g. `pkg.latest zester-peel` running apt) kills watchdog+peel+apt+dpkg mid-unpack. postinst only no-op *starts*, never restarts. INVARIANT: a node must never synchronously restart its own service from a job (kills its own cgroup) — detach it or use the self-update plane.

### Components (`pkg/update/`)

| File | Purpose |
|-|-|
| `slots.go` | Three-slot binary manager: current/previous/staging with atomic `os.Rename`. `Recover()` resolves partial swaps on startup. |
| `supervisor.go` | Child process lifecycle: start/stop/restart, HTTP probes (`CheckHealth` on `HealthURL`; `CheckReady` on `ReadyURL`, falling back to `CheckHealth` when empty; `checkEndpoint` accepts status `ok` OR `degraded` — degraded is not probe-fatal), exponential-backoff auto-restart (1s→60s). After 10 consecutive failed restarts: slow-retry tier (`SupervisorConfig.DegradedRetryInterval`, default 10m), recovers automatically when the child comes back — degraded is not terminal. `HealthVersion` parses the `/healthz` `version` field for fleet status. |
| `manifest.go` | `Manifest` struct (msgpack; `MinProtocol` gates rollouts against the fleet's reported protocol) + KV CRUD via `ManifestStore`. `BinaryStore` wraps `jetstream.ObjectStore` for chunked upload/download with SHA-256 verification. |
| `handler.go` | Watchdog-side NATS command handler. **Component gate**: the command subject is id-only (`zester.update.cmd.<id>`) and a colocated master+peel watchdog pair shares the node id, so `handleMessage` DROPS (silently — no reply; the matching colocated watchdog is the responder and an error reply would race it) any command whose non-empty `Component` mismatches `HandlerConfig.Component`; empty component is grandfathered with a Warn; every sender stamps it (rollout controller + `zester update rollback`). State machine: `idle → preparing → staged → applying → soaking → confirmed` (with `rolling_back` branch). Soak loop polls READINESS (`Supervisor.CheckReady`) — an alive-but-functionally-dead child (NATS-disconnected → `/readyz` 503) fails soak and auto-rolls back. Entering `soaking` arms a **confirm-deadline** (`HandlerConfig.ConfirmDeadline`, default 3×SoakTime floored at `MinConfirmDeadline`=5m): if neither confirm nor rollback arrives (dead/orphaned controller), the node auto-rolls back. Restart monitoring and `WaitForHealthy` use liveness. Caveat: a NATS outage during a node's soak window rolls it back even if the binary is fine — avoid rollouts during planned NATS maintenance. |
| `status.go` | `NodeStatus` + `Reporter` writing to `update-status` KV every 30s (TTL 60s = heartbeat). `NodeStatus.Degraded` (msgpack additive) via `ReporterConfig.DegradedFn`; `NodeStatus.Protocol` (additive) from `ReporterConfig.Protocol` (the watchdog passes `proto.ProtocolVersion`). |
| `rollout.go` | `RolloutController` on master: prepare → apply → soak → confirm per batch; `RequestFunc` abstraction for testability; `RolloutStore` persists to KV. **Resume**: `RolloutState.DriverID`/`DriverHeartbeat` (per-rollout 10s heartbeat); `ResumeOrphaned`/`RunResumeLoop` (every master, 60s scan) CAS-adopt non-terminal, non-dry-run rollouts whose heartbeat is staler than `StaleAfter` (default 60s), resuming from the persisted batch — a resumed batch re-issues prepare, so nodes past it reject the duplicate and count toward MaxFailed (backstopped by the confirm-deadline rollback). `StartRollout` excludes `Degraded` nodes (Info-logged; error if that empties the set) and REFUSES when any target's `NodeStatus.Protocol` is below the manifest's `MinProtocol` (0 disables). `AbortRollout` CAS-writes `RolloutAborted` even when not locally active; state saves retry with CAS-conflict classification (external abort / superseded adopter); a final mid-run persistence failure loudly aborts, while ctx cancellation (master shutdown) leaves the record for adoption. |

### NATS Resources

KV buckets: `update-manifests` (history 5), `update-status` (TTL 60s, history 1), `update-rollouts` (history 10). Object Store: `update-binaries` (TTL 30 days). Subjects: `zester.update.cmd.<id>` (master→watchdog request/reply); watchdog→master status flows via `update-status` KV heartbeats (no event subject).

### CLI Commands

`zester update publish <path> --component peel --version v0.5.0 [--ttl 720h]` (upload binary + manifest; per-version TTL, 0=never) · `zester update promote|demote|set-ttl --component peel --version v0.5.0` (promotion lifecycle: promoted = never expires + auto-rollout target; set-ttl refuses promoted versions — demote first) · `zester update auto [on|off|status]` (fleet-wide auto-rollout switch in NATS, DEFAULT ON — safe because only PROMOTED versions auto-roll; masters also honor `update_auto_rollout` + `update_auto_*` tuning knobs, `internal/masterd/updateplane.go`: deterministic `rol-auto-<comp>-<ver>-r<N>` generation ids CAS-dedup racing masters, never downgrades, one rollout per component, aborted auto-rollouts never auto-retry, completed generations re-converge late/offline nodes with the next generation) · `zester update rollout --component peel --version v0.5.0 [--batch-size 1] [--soak-time 60s]` · `zester update rollouts` (history list) · `zester update status [--rollout <id>]` (incl. DEGRADED/PROTO columns; Node Results stable-sorted with BATCH column) · `zester update abort <rollout-id>` · `zester update rollback --component peel --target '*'` · `zester update versions --component peel` (PROMOTED/EXPIRES columns) · `zester update unpublish --component peel --version v0.5.0 [--force]` (refused while a live rollout references it; --force required for promoted). **Expiry is manifest-driven**: the update-binaries bucket has NO TTL; a lease-gated hourly master GC (`pkg/update/gc.go`) reaps expired non-promoted versions (object first, manifest last; skips active-rollout refs; orphan sweep with 1h publish-in-progress grace). Legacy manifests expire at published+30d.

### Watchdog Binary (`cmd/zester-watchdog/`)

Uses `flag` package. **`--component peel|master` is the only required flag; everything else is DERIVED from the component + the child's config (`cmd/zester-watchdog/derive.go` `deriveComponentDefaults`, run post-`flag.Parse`; explicit flags win via a `flag.Visit` set — same pattern as `config.ApplyVisited`).** Per-component defaults: `--child-bin` = `/usr/local/bin/zester-{peel,master}`; `--child-args` = `--config /etc/zester/{peel,master}.yaml` ONLY when that file exists (the child fatals on an explicitly passed missing config but runs on defaults with no flag — `deriveChildArgs`); then the child config is read (tolerantly — missing = defaults) for `auth_dir`/`data_dir`/`health_addr`/`nats_ca`/`id`, and any child flag override inside `--child-args` (`--id`/`--auth-dir`/`--data-dir`/`--health-addr`/`--nats-ca`, via `argValue`) is overlaid on top (the child applies flag > YAML, so the derivation must too). Derives `--nats-creds` = `<auth_dir>/<id>.creds` (peel) or `<auth_dir>/master.creds` (master), `--nats-ca` = config `nats_ca` else `<auth_dir>/nats-ca.crt`, `--bootstrap-cache` = `<data_dir>/nats-bootstrap.msgpack` (peel only), `--health-url` = `http://<health_addr>/healthz` (fixes the old :9090-vs-:9091 footgun). `--id` = the peel config `id` (master has none → pin/hostname); BOTH an explicit `--id` and the derived one are resolved+sanitized via `config.ResolveNodeID` (SAME source + node-id pin the peel uses, so they can't disagree — a dotted `--id` maps to the same `<id>.creds` the peel writes). Packaged units are now just `ExecStart=zester-watchdog --component {peel,master}` (no ZESTER_PEEL_ID drop-in). Remaining flags (still overridable): `--nats-url` (default `tls://localhost:4222`; NOT derived — peel's discovery sentinel is empty, master's compose default differs), `--ready-url` (default `""` = derived from `--health-url` → `/readyz`; polled only during soak; restart monitoring stays on `--health-url` liveness), `--health-timeout`, `--health-interval`, `--health-retries`, `--soak-time`, `--log-level`, `--log-format` (defaults info/json via `internal/logging`). Enrollment-aware: starts the child immediately, offline mode if creds missing, polls for the creds file every 10s, connects to NATS when creds appear. Validates `tls://` NATS URLs before starting the child; NATS/bucket setup failures are retried with backoff (never exits and orphans the child); the child is stopped on every exit path. Reports `NodeStatus.Protocol = proto.ProtocolVersion`.

### ObjectStoreAPI Interface

`pkg/bus/kv.go` defines `ObjectStoreAPI` (separate from `JetStreamAPI`): `CreateOrUpdateObjectStore`, `ObjectStore`, `DeleteObjectStore` — avoids breaking `bustest.FakeJS`, which doesn't implement Object Store methods. `InitializeObjectStores()` is called separately from `InitializeStorage()`; both delegate to `...Opts` variants that apply the replicas tiering.

## Conventions

- Error wrapping: `fmt.Errorf("pkg: operation: %w", err)`
- Logging: daemons bootstrap via `internal/logging.Setup(w, component, level, format)`; library packages take a `*slog.Logger` via config structs, defaulting to `slog.Default()`
- Config knobs: `flag:"..." usage:"..."` struct tags on daemon config structs; `config.BindFlags` + `config.ApplyVisited` (`internal/config/bind.go`) generate flags and enforce flag > YAML > default — never hand-write flag blocks or `flag.Visit` switches
- KV bucket names: constants in `pkg/bus/kv.go` (BucketFacts, BucketJobs, BucketPeelHeartbeat, BucketLeases, BucketReactorFiles, etc.); stream names too (StreamJobEvents, StreamEvents)
- Object Store bucket names: constants in `pkg/bus/kv.go` (ObjectBucketUpdateBinaries)
- Subject naming: `zester.<category>.<target>` pattern, helpers in `pkg/bus/subjects.go` (incl. `zester.target.resolve`, `zester.admin.enroll.*`, `JobAckSubject`, `PeelEventSendSubject`/`BeaconSubject`/`MasterEventSubject`/`AdminEventSendSubject`, `SubjectReactorTest`)
- Wire/KV struct evolution: additive-only msgpack (`,omitempty`), per the `pkg/proto` policy — mixed-version fleets must stay safe
- Changelog: every user-visible change (feature, fix, behavior change, new flag/metric/subject) MUST append an entry under the [Unreleased] section of CHANGELOG.md in the same commit (Keep a Changelog format; moved to a version heading at release time).
